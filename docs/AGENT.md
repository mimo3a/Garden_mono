# AGENT.md — правила исполнения плана

Этот файл задаёт, **как** агент выполняет задачи из `docs/ROADMAP.md` и `docs/roadmap/*.md`.
Архитектура, протокол, ветки и инженерные ограничения — в `CLAUDE.md` в корне репозитория.
Работа над поливом, насосом, AI-агентом, approvals и audit log — по `docs/AI_AGENT_PLAN.md` и его правилам; этот файл там действует только в части, не противоречащей ему.

**Приоритет при конфликте:** `CLAUDE.md` > `docs/AI_AGENT_PLAN.md` (в своей области) > `AGENT.md` > `ROADMAP.md` > `docs/roadmap/*.md`.
При конфликте: остановиться, описать конфликт, ждать решения Алекса.

---

## 1. Выбор задачи
1. Прочитать `CLAUDE.md` и `docs/ROADMAP.md`.
2. Текущая веха — первая с непоставленным `[x]` у строки «Веха … завершена».
3. Задача — **первая по порядку в списке текущей вехи**, у которой в файле компонента статус `[ ]` и выполнены все зависимости (`Зависит от`). Задачи со статусом `[~]` и `[!]` пропускаются.
4. Если Алекс назвал задачу явно — выполнять её, даже вне порядка, но проверить зависимости и сказать, если они не выполнены.
5. Прочитать целиком: описание задачи, все файлы из поля `Файлы` и код, который задача меняет. Не править код по памяти и по фрагментам.

## 2. Согласование (обязательно)
- **В начале каждой вехи** — кратко представить план вехи: задачи, порядок, риски, что нужно от Алекса (железо, решения, доступы). Ждать одобрения. Это требование `CLAUDE.md`.
- **Перед каждой задачей** с маркером `[DECISION]` или `[COORD]` — отдельно согласовать решение, даже если веха одобрена.
- Обычные задачи внутри одобренной вехи выполнять без повторного вопроса.
- Новые зависимости (библиотеки, actions, Docker-образы) и изменения схемы существующих таблиц — всегда согласовать.

## 3. Маркеры задач
| Маркер | Значение | Что делает агент |
|---|---|---|
| `[HW]` | Нужна проверка на железе | Готовит код и пошаговую процедуру проверки (что подключить, что ожидать, как понять, что не так). Ставит `[~]`, сам в `[x]` не переводит. |
| `[COORD]` | Меняется payload, протокол или контракт API | Правит все затронутые компоненты (STM32, ESP32, `MqttMessageHandler.java`, frontend, документация) в одной ветке. Порядок выкатки — от принимающей стороны к отправляющей (backend → frontend → ESP32 → STM32), чтобы каждый промежуточный шаг был совместим. |
| `[DECISION]` | Нужен выбор Алекса | Предлагает 2–3 варианта с плюсами и минусами и рекомендацией, ждёт выбора. Выбор записывает в задачу строкой `Решение (дата): …`. |
| `[CUBEMX]` | Нужна правка `.ioc` | `.ioc` вручную не трогает. Пишет Алексу точные шаги в CubeMX (вкладка, параметр, значение), после регенерации проверяет diff. |

## 4. Правила работы с кодом

### Общие
- **Ветки** — по `CLAUDE.md`: `feature/<id>-<кратко>` от `develop` → PR в `develop`. В `main` напрямую не коммитить. Одна задача — одна ветка; задачи `[COORD]` — одна ветка на весь набор изменений.
- **Коммиты:** `<компонент>: <ID> описание`. Префиксы: `fw:` (L476), `esp:`, `backend:`, `frontend:`, `ops:`, `docs:`.
- **Запрещено** (из `CLAUDE.md`): прошивать устройства, деплоить, заходить на сервер, класть секреты в репозиторий, менять GitHub secrets.
- Изменения payload, формулы батареи, протокола — обновлять `CLAUDE.md`, `README.md`, `docs/protocol.md` в той же ветке.
- Найденный попутно баг — **не чинить попутно**: новая задача в раздел «Задачи, найденные при работе» файла компонента с пометкой `(найдено при <ID>)`.

### Прошивка STM32L476 + FreeRTOS
- Правки сгенерированных файлов (`main.c`, `freertos.c`, `stm32l4xx_it.c`, `stm32l4xx_hal_msp.c`) — **только внутри `USER CODE BEGIN … END`**.
- Логика — в модулях `Core/App/` и `Core/MyLib/`; чистые функции без HAL — с хост-тестами.
- В задачах FreeRTOS: без `HAL_Delay` и `HAL_MAX_DELAY`; каждое ожидание с таймаутом; из ISR — только `FromISR`-API; общая периферия — под мьютексом; размеры стеков — с запасом и проверкой `uxTaskGetStackHighWaterMark` в debug-сборке.
- Каждый путь low-power-кода имеет таймаут; устройство не должно остаться бодрствующим из-за сбоя связи.
- Сборка после изменений — без ошибок и **без новых warnings** (базовый список — `L476/BUILD.md`).
- V1 (F103) выведен из работы и не поддерживается; ветка `v1-f103` — архив, правок в ней нет.

### ESP32
- Сборка `cd ESP && pio run` (с копией `secrets.h.example`, как в CI).

### Backend
- `./mvnw test` зелёный. Новая логика разбора и валидации — с unit-тестами.
- После BE-0-2 изменения схемы — только миграциями Flyway, никогда правкой существующей миграции.

### Frontend
- `npm run lint`, `npm test`, `npm run build` (после FE-0-1) зелёные.
- Логика — в `src/utils/` с тестами.

### Если собрать или проверить нельзя
Нет тулчейна, нет доступа к компоненту, нет железа — сказать прямо, поставить `[~]` или `[!]` с причиной. Не выдавать непроверенное за проверенное.

## 5. Статусы задач
- `[ ]` — не начата
- `[>]` — в работе (агент ставит при старте)
- `[~]` — код готов, ждёт проверки на железе, ревью PR или решения
- `[x]` — выполнена и проверена
- `[!]` — заблокирована (причина в строке `Заметка`)

При смене статуса дописать строку:
`Заметка (ГГГГ-ММ-ДД): что сделано / ветка / PR / что проверить`

В `[x]` агент переводит задачу с `[HW]` только после подтверждения Алекса. Веху — когда все её задачи `[x]` и выполнен критерий из `ROADMAP.md`, тоже после подтверждения.

## 6. Отчёт после задачи
Коротко:
1. Что изменено (файлы, функции).
2. Результат сборки и тестов.
3. Процедура проверки на стенде — для `[HW]`; порядок выкатки — для `[COORD]`.
4. Риски и последствия для других компонентов.
5. Следующая задача по плану.

## 7. Если что-то пошло не так
- Сборка или тесты сломались и причина неочевидна → откатить свои изменения, описать проблему, поставить `[!]`.
- Задача оказалась больше описанной → предложить разбиение на подзадачи (`FW-2-2a`, `FW-2-2b`…) и ждать одобрения.
- Описание задачи противоречит реальному коду (план составлен 2026-10-25 и мог устареть) → не подгонять код под план: описать расхождение и предложить правку задачи.
