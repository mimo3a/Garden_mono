# Backend — Spring Boot 3.5, Java 21

Порядок выполнения задаётся вехами в `docs/ROADMAP.md`. Правила — `docs/AGENT.md`.
Код: `garden-backend/` (пакет `com.example.garden`). Сборка и тесты: `cd garden-backend && ./mvnw test`.

## Исходное состояние (на 2026-10-25)
- `MqttMessageHandler` подписан на `smartgarden/+/data`, `deviceId` — из топика. Каждое поле — отдельная строка `Measurement(type, value, timestamp)`; `timestamp` — `LocalDateTime.now()` при каждой записи.
- Ошибки разбора — `e.printStackTrace()`, сообщение теряется. Без массива `soil` — `NullPointerException` после создания `Sensor`. Элемент `null` в `soil` → `asDouble()` → сохраняется `0.0`.
- `soilRaw`, `adsReady` не сохраняются.
- `GET /api/sensors/{id}/history` возвращает **всю** историю без пагинации; индексов кроме PK нет.
- Схема через `ddl-auto=update`, миграций нет. **Тестов нет** (`src/test` отсутствует).
- Сессионная аутентификация + CSRF, роли `ADMIN`/`USER`, доступ через `SensorAccessService`.

    - **фильтр F103:** если `soilRaw[i] == 0` — канал `soilN` не сохраняется (на F103 `0` означает ошибку чтения ADS, а не мокрую почву; реальные значения ~7000–17300). Фильтр работает без перепрошивки установленного F103 (`v1-f103`) и применяется только к payload без `modules`;

    - тесты на реальных примерах: payload F103 из `CLAUDE.md`; F103 со сбоем ADS (`soil` 100, `soilRaw` 0); пример V2 из `docs/protocol.md`; V2 с `absent`/`error`/`-3`; расхождение `modules` и кодов; `ts: null`; `ts` из будущего; отрицательная температура; мусор.
  - Решить: сохранять ли неотрицательный `soilRaw` (нужно для перекалибровки задним числом) — новый тип `soilRawN`, схема не меняется.

- [ ] **BE-1-2. Метаданные устройства** `[COORD]`

- [ ] **BE-1-3. Идемпотентный приём по `deviceId + sid + seq`** `[DECISION]`
  - Зависит от: BE-0-2, BE-1-1
  - Спецификация — `docs/protocol.md`, разделы 4–5. Изменение схемы — **только после согласования**, миграцией Flyway.
  - Проблема: ESP досылает измерения из очереди; без ключа повтор создаёт дубли. `ts` ключом быть не может (бывает `null`).
  - Решено (2026-10-25): ключ уникальности — **`deviceId + sid + seq`**. `sid` — случайный uint32, ESP генерирует его при первой инициализации NVS; после стирания NVS приходит новый `sid`, поэтому сброс `seq` не нужно распознавать эвристиками.
  - Открыто только устройство схемы:
    - (a) таблица `reading(id, sensor_id, sid, seq, device_ts, received_at)` с уникальным `(sensor_id, sid, seq)`, `Measurement` ссылается на `reading`;
    - (b) колонки `sid`, `seq` в `Measurement` и уникальный индекс `(sensor_id, type, sid, seq)`.
    - Рекомендация: (a) — одно сообщение = одна строка `reading`, проще ack и диагностика.
  - `sid`/`seq` хранить как `bigint` (uint32 не помещается в `int` Java/PostgreSQL).
  - Payload без `sid`/`seq` (F103, V1) — без проверки дублей. Payload с `seq`, но без `sid` — отклонять с `log.warn` (нарушение протокола V2).
  - Тесты: повтор того же сообщения → одна запись; два разных `seq` → две записи; тот же `seq` с другим `sid` (стирание NVS) → новая запись; конкурентная доставка двух копий (уникальный индекс, а не проверка «select, потом insert»).

- [ ] **BE-1-4. Подтверждение записи: топик `ack`** `[COORD]`
  - Зависит от: BE-1-3, OPS-1-2 (ACL для `ack`)
  - Проблема: backend не умеет публиковать в MQTT (`MqttConfig` — только входящий адаптер).
  - Сделать: исходящий адаптер Spring Integration; после **фиксации транзакции** (`@TransactionalEventListener(AFTER_COMMIT)` или аналог) публиковать `smartgarden/{deviceId}/ack` с `{"sid":…,"seq":…,"ts":…}`; для дубля — тоже ack; невалидное сообщение — без ack. Этот же адаптер понадобится для команд полива (`AI_AGENT_PLAN.md`, ESP-3-1).
  - Тесты: ack после успешной записи; нет ack при ошибке записи; ack на дубль.
