# ESP32 — шлюз UART → Wi-Fi → MQTT

Порядок выполнения задаётся вехами в `docs/ROADMAP.md`. Правила — `docs/AGENT.md`.
Код: `ESP/src/main.cpp` (Arduino + PlatformIO, плата `esp32doit-devkit-v1`, дисплей ST7789 через TFT_eSPI).

## Исходное состояние (на 2026-10-25)
- Цикл из `setup()`: `MEASURE` → Wi-Fi (таймаут 20 с) → ожидание JSON до 60 с → MQTT (таймаут 15 с) → publish → `OK` → deep sleep 60 мин. Все пути с таймаутами.
- JSON распознаётся по `startsWith("{")`/`endsWith("}")`; топик строится из `deviceId` внутри payload, иначе из `DEVICE_ID = 2`.
- `PubSubClient` с размером буфера по умолчанию (256 байт).
- Статический IP `192.168.178.100` зашит в код; MQTT без TLS, порт 1883.
- Секреты — `include/secrets.h` (не в git), шаблон `secrets.h.example`.
- CI: `esp32-build.yml` только на push в `main`.

## Справка для агента
- Прошивать ESP32 запрещено; сборка — `cd ESP && pio run`.
- Любые новые секреты — только в `secrets.h.example` как плейсхолдеры.
- Совместимость с F103 (V1) не требуется — V1 выведен из работы; ESP работает только с L476.

- [ ] **ESP-1-1. Буферы, разбор JSON и ранний `OK`** `[COORD]`
  - Проблемы:
    - приёмный буфер `Serial2` по умолчанию 256 байт, `setRxBufferSize` в коде не вызывается; JSON приходит, пока ESP подключается к Wi-Fi и не читает UART — payload V2 (~315 байт, до 374) **обрежется ещё до MQTT**;
    - `PubSubClient` держит пакет 256 байт — `client.publish()` вернёт `false` без внятной причины.
  - Сделать (контракт — `docs/protocol.md`, раздел 3):
    - `Serial2.setRxBufferSize(1024)` **до** `Serial2.begin()`;
    - лимит строки `PAYLOAD_MAX_LEN = 512` (с `\n`), длиннее — отбросить целиком;
    - `client.setBufferSize(1024)`; константы — в одном месте;
    - проверка строки через ArduinoJson (`deserializeJson`) вместо проверки скобок; невалидные строки — в лог и пропуск, ожидание продолжается до таймаута 60 с;
    - **`OK` сразу после валидного JSON**, до Wi-Fi и MQTT (STM засыпает, не дожидаясь сервера); без валидного JSON `OK` не отправлять — как сейчас;
    - логировать длину payload и результат publish.
  - Новая зависимость `bblanchon/ArduinoJson` — согласовать (правило `AI_AGENT_PLAN.md`: ask before adding dependencies).
  - Проверка: `pio run`; на стенде — payload длиной 400+ байт приходит целиком при подключении к Wi-Fi 5+ с.

- [ ] **ESP-1-2. Топик по `DEVICE_ID` шлюза** `[DECISION]`
  - Проблема: топик берётся из тела сообщения — устройство без `deviceId` (текущий L476) уходит под чужим ID, а ошибка в прошивке STM может записать данные в чужую группу.
  - Варианты:
    - (a) топик всегда из `DEVICE_ID` шлюза; `deviceId` в payload только сверяется, при расхождении — предупреждение в лог;
    - (b) как сейчас — из payload;
    - (c) `DEVICE_ID` в `secrets.h` / NVS, payload без `deviceId`.
  - Рекомендация: (a), `DEVICE_ID` перенести в `secrets.h` (разные устройства — разные файлы, код один).
  - Связано: FW-2-1 (нужен ли `deviceId` в прошивке STM).

- [ ] **ESP-1-3. Надёжное пробуждение STM32** `[COORD]` `[HW]`
  - Зависит от: FW-3-3 (выбор механизма пробуждения на L476)
  - Сделать: преамбула (`\n`) → пауза (длительность — по времени пробуждения STM из FW-3-3, по умолчанию 50 мс) → `MEASURE`. Если за N секунд нет JSON — повтор `MEASURE`, до 3 раз, затем общий таймаут 60 с как сейчас. Порядок прошивки и совместимость со старой STM описать в отчёте.

## ESP-2. Безопасность и конфигурация

- [ ] **ESP-2-1. MQTT через TLS** `[COORD]` `[HW]`
  - Зависит от: OPS-1-3
  - Сделать: `WiFiClientSecure`, порт 8883, проверка сервера по CA-сертификату (CA — в `secrets.h`, не отключать проверку через `setInsecure()`); синхронизация времени (SNTP) с таймаутом, если требуется для проверки сертификата; отдельный MQTT-пользователь на устройство.
  - Учесть: TLS-рукопожатие увеличивает активное время и ток — замерить (`docs/power.md`).

- [ ] **ESP-2-2. Конфигурация без перепрошивки** `[DECISION]`
  - Проблема: статический IP, шлюз и DNS зашиты в код; интервал сна — константа.
  - Варианты: (a) всё в `secrets.h`, DHCP по умолчанию, статический IP опционально; (b) NVS + captive portal (WiFiManager); (c) удалённая конфигурация через retained MQTT-топик `smartgarden/{id}/config`.
  - Рекомендация: (a) сейчас; (c) — вместе с ESP-3-1, если он выберет MQTT-команды.

- [ ] **ESP-2-3. Метка времени измерения `ts` (SNTP)** `[DECISION]`
  - Зависит от: ESP-1-1
  - Спецификация — `docs/protocol.md`, раздел 4. Нужна до ESP-2-1 (TLS проверяет срок действия сертификата) и ESP-2-4 (повторная отправка с исходным временем).
  - Сделать: SNTP при каждом пробуждении с таймаутом; `ts = время_SNTP − (millis() − момент получения JSON) / 1000`; без SNTP — `ts: null` (часам ESP в deep sleep не доверять: у DevKit нет кварца 32 кГц). Поле добавляется к JSON от STM при повторной сериализации (ArduinoJson).
  - Решить: NTP-сервер (`pool.ntp.org` или локальный роутер) и таймаут; влияние на время активной фазы — замерить (`docs/power.md`).
  - Вариант на будущее (не в этой задаче): RTC STM32 с LSE, время задаёт ESP командой `TIME`.

- [ ] **ESP-2-4. Подтверждение сервера и очередь неотправленных** `[COORD]` `[DECISION]` `[HW]`
  - Зависит от: ESP-1-1, ESP-2-3, BE-1-3, BE-1-4
  - Спецификация — `docs/protocol.md`, разделы 1, 4–7.
  - Сделать:
    - `sid` (uint32, ≠ 0): при первой инициализации NVS (пустой или стёртый) сгенерировать аппаратным ГСЧ (`esp_random()` при включённом радио или после `bootloader_random_enable()`), сохранить в NVS, дальше не менять;
    - счётчик `seq` (uint32) в NVS в пределах `sid`: при новом `sid` начинается с 1; увеличить и сохранить при получении валидного JSON **до** первой отправки;
    - поля `sid` и `seq` в MQTT-payload; повторная отправка — с исходными `sid`, `seq` и `ts`;
    - подписка на `smartgarden/{DEVICE_ID}/ack` до публикации; ожидание ack на каждую пару `sid` + `seq` с таймаутом `SERVER_ACK_TIMEOUT_MS` (ориентир 5 с); ack с чужим `sid` игнорировать;
    - неподтверждённые записи — в ограниченную очередь `QUEUE_MAX`; при следующем пробуждении досылать от старых к новым, затем текущее; при переполнении вытеснять самую старую;
    - отправка очереди не продлевает активную фазу сверх общего таймаута цикла.
  - Решить — место очереди:
    - (a) RTC-память (`RTC_DATA_ATTR`, 8 КБ): быстро, без износа Flash; теряется при сбросе питания и brownout;
    - (b) LittleFS: переживает сброс; ~24 записи в сутки — износ незначителен;
    - и `QUEUE_MAX` (ориентир 24 — сутки без сервера).
  - Проверка `[HW]`: сервер остановлен на 3 цикла → после запуска приходят все измерения с исходными `ts`, без дублей в БД; потеря ack при записанных данных (остановить backend сразу после записи) → повтор не создаёт дубля; сброс питания ESP → `sid` прежний, `seq` продолжается; стирание NVS (`pio run -t erase`, выполняет Алекс) → новый `sid`, `seq` с 1, backend принимает новые измерения.

## ESP-3. Команды к устройству

- [ ] **ESP-3-1. Доставка команд при deep sleep** `[DECISION]`
  - Предусловие для фазы 1 `docs/AI_AGENT_PLAN.md` (полив). Решение принимается **до** начала фазы 1.
  - Проблема: ESP32 спит 60 минут — команда полива от backend может ждать до часа; при этом в спящем режиме ESP не подписана на MQTT.
  - Варианты:
    - (a) retained-сообщение / сессия QoS 1 с `cleanSession=false`: ESP при пробуждении забирает команду, выполняет, публикует ACK — задержка до интервала сна;
    - (b) сокращённый интервал пробуждения только для проверки команд (без измерения) — больше расход;
    - (c) узел полива на постоянном питании отдельно от батарейного узла датчиков.
  - Сделать: сравнение с оценкой тока (из `docs/power.md`) и задержки; решение записать в `docs/AI_AGENT_PLAN.md` как входные данные фазы 1.
